# Phase 10.4 — Business/Demo Consistency\n\n## Scope\n\nKeep the customer-visible business story consistent across service pricing, wallet accounting, activation/order history, notifications, and lifecycle status.\n\n## Completed\n\n- Service price is read from the PostgreSQL catalog at purchase time.\n- The same authoritative price is persisted on the activation and used for the wallet debit.\n- Successful cancellation sets the refund amount from the activation charge and credits exactly that amount.\n- Activation wallet references remain single-entry keyed, preventing duplicate debit/refund credits for the same activation reference.\n- Customer order history now exposes the order reference and refund amount for refunded orders.\n- Customer activation purchase/cancellation mutations refresh wallet, activation history, and notifications together.\n- Notification synchronization now backfills CancellationPending as well as terminal activation states.\n- Lifecycle status grouping remains aligned: Active, CancellationPending, and ExpirationPending are ongoing; Completed, Expired, Refunded, and Cancelled are history.\n\n## Release invariant\n\nFor a customer activation, the displayed catalog price at purchase, activation pricePaise, wallet debit, order history amount, and any successful cancellation refund must describe the same transaction. Notification state must point to the same activation/order and its latest persisted lifecycle state.\n\n## Verification target\n\nCI must pass the dedicated Phase 10.4 regression coverage plus the repository test suite. Production verification must confirm service-price integrity, wallet reconciliation, activation state/notification coverage, and scheduled reconciliation health.
